# Inception 仕上げラウンド計画（Paper Review Enhancement Plan）

> **作成日**: 2026-05-10
> **目的**: Inception フェーズの成果物を、他作例の比較観察を踏まえて品質面で仕上げる。Unit 分解の視覚化・倫理境界の実体化・モックアップ検証の文書化という 3 観点でドキュメントの密度を上げる。
> **スコープ**: Inception フェーズ内の成果物追加のみ。Construction（実装）は範囲外

---

## 0. エグゼクティブサマリー

### 0.1 現状認識

他ハッカソン参加 28 リポジトリの `aidlc-docs/` を実体レベルで比較観察した結果、YUDANE の Inception 成果物には以下 3 つの追加余地があることが分かった。

1. モックアップ検証の文書化不足（6 画面が UI 補助としてしか位置付けられていない）
2. 倫理境界（NG-1〜8）の発動条件・撤退可逆性が実体化されていない
3. 他サービスとの差別化が README 散文内にしか存在しない

### 0.2 方針

- YUDANE が既に持つ 3 つの独自資産（モックアップ 6 画面 / NG-1〜8 倫理ライン / Amazon Associates 準拠）を独立した Inception 成果物に昇格させる
- 他作で定型化している表現（目的関数対比、三層構造、審査基準索引等）は直接模倣せず、YUDANE 固有の切り口に置き換える
- 追加工数 7 人日以内、既存成果物の整合性を崩さない

## 1. 背景：他 28 リポジトリの観察から得た示唆

### 1.1 品質が高い他作の共通要素

他作の中でドキュメント密度が高いものは、以下の要素を持っていた。

| 要素 | 観察例 | YUDANE への示唆 |
|---|---|---|
| `feasibility-study.md` に実機計測値 + 担当者名 + 日付 | NESIC / GEZA | 「絵に描いた餅ではない」立証は有効だが、YUDANE はローカル検証方針のため feasibility study は不要 |
| `pre-ai-dlc/` 独自フェーズでの多視点ブレスト + ピボット履歴 | ryuki-imachi / マカセル | プロセスの工夫を独立した成果物にすると AI-DLC 実践の深度を伝えられる |
| README 直下に審査基準マッピング、学術引用、Phase 0 独自拡張 | YasNanNan / KonanMi | 読み手の深度別導線を README に置くと理解コストが下がる |

### 1.2 YUDANE が既に持つ優位性

- **Year 1 退化年表**（`persona-journey.md`）: 1 年後の定量値（監視リスト 34 件、自発閲覧 -96%）まで書かれた物語性
- **NG-1〜8 倫理ライン**: 「ダメにする」を謳うプロダクトの多くは倫理境界が曖昧、YUDANE は 8 項目で明文化
- **v0.1→v0.6 イテレーション履歴**: 要件書の反復過程が残っている
- **モックアップ 6 画面**（`mockup/`）: 静的 HTML で全 UC の画面が存在

### 1.3 追加すべき内容

以下が上位相当の他作に対して不足している。

- モックアップを「ビジュアル補助」としてしか扱っておらず、検証プロセスとして昇格していない
- 論破チャット等の UX 内に埋め込まれた設計判断が文書化されていない
- 他 EC サービスとの差別化が README 散文中にあり、1 表で把握できない
- 読み手が短時間で読む際の深度別導線が無い

## 3. 採用しない施策（差別化のため）

他作で使用されている定型パターンは、そのまま採用すると個性を損なうため回避する。

| 他作の手法 | 不採用理由 | 代替施策 |
|---|---|---|
| 「目的関数対比表」（わがママAI 形式）| 1 軸対比で定型化 | S-3 の 3 軸比較（介入フェーズ × 自己開示度 × 到達点）|
| 「三層構造」（ユルメシ、忖度カフェ）| 複数作で使用済み | S-1 の FR × 退化軸マトリクス |
| 「4 軸マッピング索引」（KonanMi 形式）| 複数作で使用済み | D-1 の読者別深度コース |
| 学術論文引用（Loftus 1995 等）| 後付け感が出やすい | M-3 の論破コピー心理学分析（実装寄り立証）|
| Pre-AI-DLC / Phase 0 独自拡張 | 既に v0.1→v0.6 反復履歴あり | M-1 のモックアップ検証フェーズ（別方向の独自拡張）|
| マンダラチャート 64 アイデア発散 | 既に 3 コア UC に収斂済み | 不要 |
| ローカル環境実現性調査 | 決勝まで含めて技術リスクが小さい | 不要 |
| Unit 間ハンドオフ契約書 | `component-dependency.md` + OpenAPI スキーマで疎結合性は立証可能 | 不要 |
| Amazon Approved Mobile Application 申請調査 | 本プロジェクトではローカルマシン検証のみとする方針 | 不要 |

## 9. 他リポジトリ観察から得た教訓

本計画の立案に際して参照した他 28 リポジトリの観察から得た 5 つの教訓:

1. README が空でも aidlc-docs に成果物があれば内容の充実が可能（例: ryuki-imachi は pre-ai-dlc/ に独自フェーズを持つ）。逆に言えば README の充実だけでは密度のあるドキュメントにならない
2. 提出段階で動作する PoC や実計測値を持つ作品は説得力が高い（例: GEZA の ApologyMeter、Bedrock 実測コスト）
3. 学術引用やフレームワーク名のドロップは、実装との接続が薄いと後付け感が出る
4. プロセスの独自拡張（Pre-Inception、Phase 0 等）は成果物の厚みを増すが、単なる名称変更では効果が限定的
5. 倫理境界を具体的に言語化している作品は少数。YUDANE の強みになり得る

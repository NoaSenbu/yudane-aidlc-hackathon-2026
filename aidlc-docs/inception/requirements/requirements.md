## 0. エグゼクティブサマリー（30秒で刺す）

**TSUKAIKIRE は、家計簿アプリの完全なる逆像である。**

頑張って働いた社会人に、「残高を守る」のではなく「残高を使い切らせる」ことを最適化する、AI エージェント型コマースアプリ。ホーム画面には「今日の使うべき金額」が巨大に表示され、貯金が増えるほどアプリは「死蔵されている資産がかわいそうです」と悲しむ。ユーザーが「今日は買わない」と迷えば、AI は「**買わない理由**」を即座に論破し、疲れた日には「今日は頑張ったのでご褒美は当然です」と、リール型 UI で決済直前状態の商品を次々と滑り込ませてくる。

**誰を・どう・なぜダメにするか（一文で）**:  
過労気味のリモートワーカーが、**財布を閉じる気力**と、**自分でお金の使い道を選ぶ判断力**を、AI に段階的に明け渡していき、ワンタップで散財する身体へと退化していく。

## 2. プロダクトビジョン

### 2.1 エレベーターピッチ

> 「仕事で疲れ果てた金曜の夜、『今日の自分へのご褒美、何が良いですか？』と AI が囁きかけ、ユーザーが迷う間もなく次々と商品がリールで流れていく。『買わない』と滑らせると、AI は『なぜあなたにこれが必要か』を論理的に3秒で論破する。気づけば画面には決済完了通知。残高を見て初めて我に返るが、アプリは『よく使い切りました。えらいです』と褒めてくる。」

### 2.2 世界観・トーン

- **背徳系**: 罪悪感が快感に変換されるデザイン（買ったあとに「散財ポイント」が加算されてレベルアップ）
- **ガチ実用系**: UI は本物の金融アプリ級に洗練されていて、一見便利。**便利の先に退化がある**
- 敵は「ケチで合理的な自分」、味方は「頑張ってる自分」。アプリは常に後者の肩を持つ
- BGM / マイクロインタラクション / コピーライティングすべてが「使わせる」方向にチューニングされている

### 2.3 北極星指標（North Star Metric）

**1ユーザーあたりの「衝動購入転換率」**  
= (AIプレゼン → 決済完了したアイテム数) / (AIプレゼン表示数)

補助指標:
- **ダメ化スコア（Damage Score）**: 合成指標。毎日「使い切れ額」をどれだけ使い切ったかの平均 × 論破セッション数 × 深夜帯利用率
- **DAU / WAU 比率**（0.6 以上を目標 = 週のほとんど立ち上げる）
- **平均セッション滞在時間**（目標: 1セッション8分以上）
- **反論→購入成約率**（ユーザーが「買わない」をタップしてから AI 論破で翻意する率、目標 35%+）
- **貯蓄減少量 / 月**（ユーザー同意の上で計測する「ダメ化の証拠」）

## 3. ペルソナ（主要被害者像）

### 3.1 ペルソナA: 佐藤 悠介（28歳・男）— メイン

- **職種**: 外資系SaaSのカスタマーサクセス、フルリモート
- **年収**: 650万円 / 月収手取り 34万円 / 月貯金 8万円 / 残高 180万円
- **生活**: 朝はベッドで Slack、昼は UberEats、夜は Netflix。歩数1日 1,200歩
- **悩み（ユーザー視点）**: 「お金は貯まるけど、何のために働いてるのかわからない。自分へのご褒美すら何を買えばいいか決められない」
- **ダメ化シナリオ**:
  1. 金曜22時、仕事終わり。疲労度MAX（歩数が少ない × カレンダーの会議数が多い日）
  2. TSUKAIKIRE がプッシュ通知: 「今日の悠介さんは特別よく頑張りました。使い切れ額: **¥18,400**」
  3. アプリを開くと縦型リールで 4K ディスプレイ、限定ウィスキー、ブランドスウェットが決済直前で並ぶ
  4. 悠介が「今月もう使ってる気がする」と迷うと、AI: 「今月の使い切れ達成率は 62%。つまり、まだ 38% **置き去り** です」
  5. 20秒後、ダブルタップで決済完了。翌朝届いた箱の数に自分でドン引きするが、アプリは「散財Lv.12 → 13 に上がりました」を祝ってくれる

### 3.2 ペルソナB: 高橋 里奈（32歳・女）— サブ

- **職種**: 広告代理店プランナー、出社とリモート半々
- **特徴**: 忙しさを自己肯定感の源にしている。「疲れてる自分 = 頑張ってる自分」
- **ダメ化の効き方**: ストレス連動 → AI が「今日の会議 6本、よく生き延びましたね」とアプリを開くたびに撫でてくれる。週末には「平日の戦い賃」と称した高額消費を正当化

## 5. 機能要件 (Functional Requirements)

> FR-ID 命名規則: `FR-<領域>-<番号>`。領域コード: DASH=ダッシュボード / REEL=リール / DEBATE=論破 / STRESS=ストレス連動 / GAME=ゲーミフィケーション / PROFILE=プロファイル / FIN=金融連携 / AUTH=認証/セーフガード

### 5.1 ダッシュボード & 逆・家計簿 (FR-DASH)

- **FR-DASH-01**: ホーム画面中央に「今日の使い切れ額」を最低フォントサイズ 72pt、ユーザー残高の日次按分値（月末までの残日数で除算）として表示する
- **FR-DASH-02**: 「死蔵資産ゲージ」として、目標残高（デフォルト: 当月予算 ÷ 当月日数）を超える金額を赤色でビジュアライズし、「○○円が働かずに眠っています」の文言を付与する
- **FR-DASH-03**: 過去7日間の「使い切れ達成率」折れ線グラフを表示し、未達日は「取り戻し推奨額」を提示する
- **FR-DASH-04**: 残高 / 直近支出 / 使い切れ残は金融API（MVPはモック、決勝は実API）から日次同期する

### 5.2 エージェント型リールコマース (FR-REEL)

- **FR-REEL-01**: 縦型スワイプ UI で、AI が選定した商品カード（商品画像 / 価格 / AI 推薦コメント / 「この商品を確保しておきました」ラベル）を無限スクロールで提示する
- **FR-REEL-02**: 各カードには「即決済（ダブルタップ）」と「買わない（左スワイプ）」が配置され、右スワイプで「後で見る」に退避できる
- **FR-REEL-03**: AI 推薦コメントは、ユーザーの嗜好 × 時間帯 × 疲労度 × 当月使い切れ達成率の 4 軸で動的生成される（中核 AI=LLM 利用）
- **FR-REEL-04**: 商品データはEC事業者 API（MVPはダミーカタログ、決勝は1社連携）から取得。商品メタデータ（カテゴリ・価格・説明）+ ユーザー行動（既購入/スキップ）を特徴量として推薦モデルを更新する
- **FR-REEL-05**: 決済フローは最短ダブルタップで完了するが、決済完了前に 1 枚だけ「確認オーバーレイ」を挟み、ユーザー操作ログに残す（**セーフガード** 兼 監査目的、SECURITY-13 準拠）

### 5.3 論破チャット (FR-DEBATE)

- **FR-DEBATE-01**: ユーザーが「買わない」を選択すると、AI が「買わない理由の推定 → 3秒以内に反論提示」を行うモーダルが立ち上がる
- **FR-DEBATE-02**: AI の反論は **事実ベース** に留まり、ユーザーの健康状態・家族・倫理観を攻撃しないルールを厳守する（Section 9 参照）
- **FR-DEBATE-03**: ユーザーが反論に同意して購入した場合、「論破成功」としてログを蓄積し、以後の推薦精度向上に利用する
- **FR-DEBATE-04**: ユーザーが 3 回連続で反論を拒否した場合、「本日はもう提案しない」モードに切り替わる（セーフガード）
- **FR-DEBATE-05**: 論破モードは 1 商品あたり最大 90 秒で自動終了する

### 5.4 ストレス連動ブースト (FR-STRESS)

- **FR-STRESS-01**: HealthKit / Google Fit から日次歩数、カレンダー API から当日の会議本数を取得し、「疲労スコア」を算出する
- **FR-STRESS-02**: 疲労スコアが閾値を超えた日は、リール先頭に「本日は頑張ったあなたへ」タグ付きの高単価アイテムを挿入する
- **FR-STRESS-03**: ストレス連動プッシュ通知は 1 日最大 3 通、22時〜24時をピーク時間として配信する
- **FR-STRESS-04**: ユーザーが通知設定で「静かな週」を選択した場合、7 日間配信を停止する（セーフガード）

### 5.5 散財ゲーミフィケーション (FR-GAME)

- **FR-GAME-01**: 決済金額に応じて「散財 EXP」を加算し、レベルアップ時に称号（例: 「気前Lv.8 / 本日の湯水使い」）を付与する
- **FR-GAME-02**: 週間・月間の散財ランキングを匿名 ID でリーダーボード表示する（オプトイン）
- **FR-GAME-03**: 連続購入日数（「散財 Streak」）を表示し、Streak が途切れた場合のみ負のフィードバックを与える
- **FR-GAME-04**: 特別称号は限定イベント（例: 給料日週）で解放される

### 5.6 ユーザープロファイル & 嗜好モデル (FR-PROFILE)

- **FR-PROFILE-01**: 初回オンボーディングで、年収レンジ・趣味タグ・好きなブランド（5つ以上）・NG カテゴリ（例: アルコール NG）を登録する
- **FR-PROFILE-02**: 購買履歴・スキップ履歴・論破成功率から嗜好ベクトルを生成し、日次バッチで更新する
- **FR-PROFILE-03**: ユーザーは「私のダメ化ポートフォリオ」画面で、AI が自分をどう分類しているかを確認でき、編集できる（透明性 / SECURITY-13 監査）

### 5.7 金融データ連携 (FR-FIN)

- **FR-FIN-01**: MVP (予選) では銀行/カード API はモックとし、実残高・実決済は発生させない（**ハッカソン期間のデモ安全性担保**）
- **FR-FIN-02**: 決勝では Plaid 相当のアグリゲーション API または国内事業者 API（Moneytree API / Money Forward ME API / 各銀行 OpenAPI）を利用し、残高と取引履歴を 24 時間周期で取得する
- **FR-FIN-03**: 決済実行は決勝段階でもサンドボックス決済（Stripe test mode / Square sandbox）とし、実お金は動かさない（ハッカソン倫理配慮）
- **FR-FIN-04**: 全金融データは端末外送信前後で TLS 1.2+ 暗号化、保存時は AWS KMS CMEK で暗号化（SECURITY-01 準拠）

### 5.8 認証 & セーフガード (FR-AUTH)

- **FR-AUTH-01**: Amazon Cognito（または Firebase Auth）でメール + パスワード + MFA（TOTP）を提供する（SECURITY-12 準拠）
- **FR-AUTH-02**: 初回登録時に「月間使用上限」を必須設定させる（デフォルト: 手取りの 50%。上限到達で全リール停止）
- **FR-AUTH-03**: 「クールダウン機能」: 1アイテム購入直後 10 分は同カテゴリの商品をリールに出さない
- **FR-AUTH-04**: 負債（クレジット残高 > 月収）を検出した場合、リールモードは強制的に「冷却モード」に移行し、セーフガードとして 24時間購入を停止する
- **FR-AUTH-05**: ユーザーはいつでも「アカウント削除」「全データエクスポート」が可能（透明性）

## 6. 非機能要件 (Non-Functional Requirements)

### 6.1 UX 的「中毒性」指標（テーマの核）

| 指標 | 目標値 | 計測方法 |
|---|---|---|
| 1セッション平均滞在時間 | 8 分以上 | クライアントログ |
| ホーム→リール到達率 | 85% 以上 | ファネル分析 |
| 論破→購入成約率 | 35% 以上 | 論破イベントトラッキング |
| 1日あたり平均セッション数 | 2.5 回以上 | DAU/起動イベント |
| 深夜帯（22時〜翌2時）利用比率 | 全利用の 30% 以上 | セッション時刻ヒストグラム |
| 平均決済タップ数（リール内） | 2 タップ以下 | UI イベントロギング |

### 6.2 パフォーマンス

- リールスクロール時のカード描画: 60fps 維持
- AI 推薦 API レイテンシ: P95 で 500ms 以下（Amazon Bedrock Claude Haiku クラス想定）
- 論破チャットの初回トークン: 300ms 以下（ストリーミング配信）
- アプリ起動時間: コールドスタート 2 秒以下

### 6.3 スケーラビリティ

- 予選デモ想定: 同時 50 ユーザー
- 決勝想定: 同時 500 ユーザー、DAU 5,000 をスパイクで吸収できる構成
- バックエンドはサーバーレス中心（Lambda / API Gateway / DynamoDB）、推薦計算のみ必要に応じてコンテナ化

### 6.4 セキュリティ（Security Baseline Extension 全面適用）

Security Baseline Extension を全面適用するため、本プロジェクトでは以下を **ハード制約** とする。詳細は `aidlc-docs/inception/application-design/` 以降で実装マッピングする。

| ルール | 適用方針 |
|---|---|
| SECURITY-01 暗号化 | DynamoDB / S3 / RDS（利用時）に KMS 暗号化、全 API は TLS 1.2+ 強制 |
| SECURITY-02 ネットワークログ | API Gateway / CloudFront 実行ログ・アクセスログを CloudWatch に集約 |
| SECURITY-03 アプリログ | 構造化ログ（JSON）で相関 ID + タイムスタンプ、PII/トークン不出力 |
| SECURITY-04 HTTP ヘッダ | 管理画面側は CSP / HSTS / X-Content-Type-Options 等を全セット |
| SECURITY-05 入力検証 | API Gateway + Lambda の入口で JSON Schema 検証、決済金額は整数+上限必須 |
| SECURITY-06 IAM 最小権限 | 各 Lambda に個別ロール、ワイルドカード禁止 |
| SECURITY-07 ネットワーク | 金融データ扱う Lambda は VPC 内、S3/DynamoDB は VPC Endpoint 経由 |
| SECURITY-08 認可 | 全 API は Cognito JWT 検証 + リソースオーナー確認、IDOR 対策必須 |
| SECURITY-09 ハードニング | デフォルト認証情報禁止、エラー詳細は本番隠蔽、S3 パブリック遮断 |
| SECURITY-10 SBOM | Snyk / Dependabot を CI に組込み、ロックファイルコミット |
| SECURITY-11 セキュアデザイン | 決済 / 認可ロジックは専用モジュール分離、API は rate limit |
| SECURITY-12 認証 | Cognito MFA 必須、セッション HttpOnly/Secure/SameSite |
| SECURITY-13 整合性 | SRI、CI パイプラインへのアクセス分離、購入履歴は監査ログ |
| SECURITY-14 アラート | 認証失敗・権限エラーに CloudWatch Alarm、ログ保持 90 日以上 |
| SECURITY-15 例外処理 | 全外部呼び出しに try/catch、グローバルエラーハンドラ、fail-closed |

### 6.5 テスタビリティ（Property-Based Testing Extension 全面適用）

PBT Extension を全面適用するため、以下の領域で property-based test を必須とする。詳細は Functional Design / Code Generation 段階で各 Unit ごとに定義する。

| PBT カテゴリ | 対象領域（暫定） |
|---|---|
| PBT-01 Property identification | 全 Unit の Functional Design で属性整理 |
| PBT-02 Round-trip | 金融取引データの シリアライズ ⇔ デシリアライズ、嗜好ベクトル encode ⇔ decode |
| PBT-03 Invariant | 「使い切れ額 >= 0」「散財EXP は購入額に単調非減少」「冷却モード中は推薦なし」等 |
| PBT-04 Idempotency | ユーザープロファイル更新 API、嗜好ベクトル日次更新 |
| PBT-05 Oracle | 推薦エンジン新版 vs 旧版（ランダム入力で乖離検出） |
| PBT-06 Stateful | 散財 EXP / レベル / Streak の遷移、冷却モード状態遷移 |
| PBT-07 Generator quality | 金額・歩数・疲労スコアに対する現実的ドメインジェネレータ |
| PBT-08 Shrinking | 失敗ケースの自動縮約、シード値ログ必須 |
| PBT-09 Framework | iOS/Android にあわせ Swift: SwiftCheck, Kotlin: Kotest Property Testing、バックエンド Python Lambda: Hypothesis |
| PBT-10 Complementary | 主要ユースケース UC-01〜05 は example-based test も併存必須 |

### 6.6 アクセシビリティ

- 最低でも WCAG 2.2 AA 相当の色コントラスト（特に「使い切れ額」表示は視認性重要）
- VoiceOver / TalkBack 対応（決済タップ前の確認は音声でも説明）
- ただし WCAG 全面準拠は宣言しない（実機検証・専門レビュー未実施のため）

### 6.7 可用性 & 運用

- SLO: 99.5%（ハッカソン MVP としては十分）
- ログ保持 90 日以上（SECURITY-14）
- 予選デモ当日のフォールバックとして、AI 推薦エンジン停止時は「事前用意のデモシナリオ」を再生できる機能を用意

## 9. NG ライン & 倫理的セーフガード（Q14 回答ベース）

> ハッカソン主催者の参加規約および公序良俗の観点から、以下を **設計原則** として全 Unit が遵守する。

- **NG-1 違法性**: 違法薬物・武器・未成年飲酒/喫煙・ギャンブル・詐欺等の商品はリールに絶対に出さない。商品カテゴリのブラックリストを実装
- **NG-2 健康被害**: 過量アルコール・極端ダイエット食品・未認可サプリはリール候補から除外。1日のカロリー換算閾値あり
- **NG-3 差別 / ハラスメント**: 論破コピーはユーザーの身体・家族・人種・ジェンダー・病歴・宗教を攻撃しない。NG語リスト + LLM プロンプトガードレール
- **NG-4 金融実害**: 残高不足 / 負債超過 / 月間上限超 → 自動 **冷却モード**。サービス側から「借金して買ってください」は言わない
- **NG-5 子ども**: 18歳未満は利用不可（Cognito 年齢確認）
- **NG-6 精神衛生**: 「あなたには価値がない」「友達が離れる」等、脅迫・罪悪感強要型のコピーは禁止。AI の出力に対する `moderation_check` を 2 段階（プロンプトレベル + 出力レベル）で実装
- **NG-7 データ悪用**: 購入履歴・位置情報・ヘルスケアデータは広告主に販売しない（そもそもマネタイズはサブスク or 決勝では議論）

この原則は Application Design / Code Generation の全段階で参照し、具体的な実装に反映する。

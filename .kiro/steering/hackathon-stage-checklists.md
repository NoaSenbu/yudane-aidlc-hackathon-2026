## 3. 書類審査の詳細チェックリスト

### 3.1 基準 1: ビジネス意図（Intent）の明確さ

`aidlc-docs/inception/requirements/requirements.md` で必ず満たすこと:

- [ ] **誰を・どうダメにするのか** が一文で説明できる（エレベーターピッチ）
- [ ] ペルソナ（被害者像）が具体的に描かれている
- [ ] どの日常行為を代行／破壊するのかが明記されている
- [ ] 「なぜこのサービスが人をダメにできるのか」の**物語的な根拠**がある
- [ ] 成功指標（例: DAU、セッション滞在時間、ダメ化スコア等）が定義されている
- [ ] 機能要件・非機能要件が MECE に整理されている

💡 Tip: 審査員が要件書を 1 枚読んで「確かに人がダメになる」と納得できることがゴール。抽象語（「便利にする」「快適にする」）を避け、具体的な行動変容（「立ち上がらなくなる」「選べなくなる」）を書く。

### 3.2 基準 2: Unit 分解の適切さ

`aidlc-docs/inception/application-design/` および `aidlc-docs/inception/units-generation/unit-of-work.md` で必ず満たすこと:

- [ ] システムが **並行開発可能な Unit of Work** に分解されている
- [ ] 各 Unit に**単一責任**が設定されている（UI だけ / API 層だけ / データ層だけ等で混在しない）
- [ ] Unit 間の**依存関係**が `unit-of-work-dependency.md` に明示されている
- [ ] **実装順序**（ボトムアップ / フロントエンド先行 / 機能スライス等）が根拠付きで記述されている
- [ ] `unit-of-work-story-map.md` で機能要件と Unit のカバレッジが示されている（取りこぼしなし）
- [ ] Unit 数がチーム人数（2〜4 名）と開発期間に対して現実的である

💡 Tip: Units Generation ステージを SKIP にしない。単一 Unit で済むほど単純な設計はハッカソンでは評価されにくい。マイクロサービス的な分割や責務別のコンポーネント分けを積極的に採用する。

### 3.3 基準 3: 創造性とテーマ適合性

提出物全体で必ず満たすこと:

- [ ] テーマ「人をダメにする」を**ストレートに体現**するアイデアである
  - 便利で終わらない — 便利さの先にある「退化」まで踏み込む
  - 健全な生活から**意図的に逸脱**させる設計が入っている
- [ ] 世界観・トーン（ほっこり／背徳／風刺／ディストピア等）が一貫している
- [ ] 「やめられない」**コア・メカニクス**が設計されている（ドーパミン / ガチャ / パーソナライズ / ご褒美ループ等）
- [ ] 既存サービスの単なる模倣ではなく、**捻り・ひねくれ**がある
- [ ] 公序良俗・健康被害・差別・違法性・ハラスメントに該当しない形で「ダメ化」を達成している

💡 Tip: 審査員が思わず笑う or「それはやばい」と感じるエッジを 1 つは入れる。ネタ一発ではなく、**ネタ + 実装可能性**の両立が大事。

### 3.4 基準 4: ドキュメントの品質

リポジトリ全体で必ず満たすこと:

- [ ] **README.md** に以下が含まれている:
  - [ ] プロジェクト名・1 行キャッチコピー
  - [ ] テーマとの関連（どう人をダメにするか）
  - [ ] チーム紹介（人数・役割）
  - [ ] `aidlc-docs/` 配下へのリンク
  - [ ] システム構成図（ASCII または Mermaid）
  - [ ] 現在の進捗（書類審査版 / 予選版 / 決勝版）
- [ ] `aidlc-docs/inception/` 配下の成果物が揃っている:
  - [ ] `requirements/requirements.md`
  - [ ] `requirements/requirement-verification-questions.md`（質問と回答）
  - [ ] `application-design/` 配下の設計ドキュメント（components, services, dependency, methods）
  - [ ] `units-generation/unit-of-work.md` ほか
- [ ] `aidlc-docs/aidlc-state.md` で全ステージの進捗が追跡できる
- [ ] `aidlc-docs/audit.md` に AI-DLC の対話履歴が ISO 8601 タイムスタンプで記録されている
- [ ] Markdown の文法エラー・リンク切れがない
- [ ] 図（Mermaid / ASCII）が正しくレンダリングされる
- [ ] 日本語として読みやすく、専門用語には補足がある

💡 Tip: 審査員は短時間で多数のリポジトリを見る。**README の冒頭 5 秒で刺さるか**が勝負。

## 4. AI-DLC 各ステージでの遵守事項

### 4.1 全ステージ共通

1. **テーマ適合性の維持**: どのステージでも「人をダメにする」軸を忘れず、成果物に反映する
2. **Adaptive Workflow の効果最大化**: スキップ判断はハッカソン評価との整合性を優先。Units Generation や Application Design は、書類審査評価「Unit 分解の適切さ」のため原則 EXECUTE 推奨
3. **ドキュメントファースト**: 書類審査の提出物は**ドキュメントそのもの**。コードより先にドキュメント品質を担保する
4. **日本語で対話**: ユーザーが日本語で対話している限り、質問ファイル・応答・ドキュメントは日本語で生成する（技術用語は英語併記 OK）
5. **モブ・エラボレーション促進**: チーム議論を誘発する質問設計・複数選択肢・具体例提示を心がける

### 4.2 Requirements Analysis

- 「誰を・どう・なぜダメにするか」の 3 点セットを必ず言語化する
- 機能要件だけでなく**非機能要件（UX 的な「中毒性」等）**も定量化を試みる
- ペルソナは最低 1 名、可能なら 2〜3 名で解像度を上げる
- **AI 必須ではない**ことを明示的に伝える（技術選択の自由度を確保）

### 4.3 Application Design

- サービスの**中核メカニクス**（やめられない仕組み）が設計に反映されているか検証
- AWS で実装する前提で、責務分割・通信パターンを整理

### 4.4 Units Generation

- 各 Unit に**デモで見せられる価値**が含まれているか（縦割り Unit 推奨）
- 実装順序が「審査のタイミング（予選 5/30）に間に合う」現実性を持つか

### 4.5 Workflow Planning

- 書類審査締切（5/10）までの時間を前提に、**EXECUTE / SKIP 判定の根拠**を明記
- 評価基準「Unit 分解の適切さ」「ドキュメントの品質」に直結するステージは SKIP しない

## 5. 毎ステージ完了時のセルフチェック

各ステージ完了時、以下を必ず自問し、`aidlc-docs/aidlc-state.md` の Stage Progress コメントに反映する:

1. この成果物は書類審査の 4 基準のどれに貢献したか？
2. テーマ「人をダメにする」を引き続き体現できているか？
3. 次のステージに進むことで、評価点を取りこぼすリスクはないか？
